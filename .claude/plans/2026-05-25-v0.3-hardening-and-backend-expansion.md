Re-engaging this requires solving the token-source problem first. See QUEUED entry "Bearer-token auth deferred — needs token-issuance story" added below.

## Phase 4 — Subprocess-isolated backend pattern [SEQ]

Architectural prerequisite for Piper + Chatterbox. Solo task, ~1 day.

### D1 [SEQ] Design + implement the subprocess pattern (QUEUED #15)

- [ ] **Design decision: IPC choice.** Options:
  - (a) Per-backend HTTP shim — backend runs its own tiny FastAPI in a subprocess; voice-forge talks to it via localhost HTTP. Familiar, supports streaming, but heavier.
  - (b) stdin/stdout JSON-line protocol — backend reads JSON-line requests from stdin, writes responses to stdout. Simpler, faster startup, but streaming is awkward (need length-prefixed binary frames over stdout).
  - (c) Unix-domain socket with line-delimited JSON + framed binary — sweet spot for low-latency local IPC.

  **Recommendation: (a)** — HTTP shim. Cost is +50-100ms per call (negligible vs synth time) and gives us streaming for free (chunked HTTP). The subprocess can also reuse FastAPI patterns; less new code.

- [ ] Implement `SubprocessBackend` abstract base in `src/voice_forge/backends/_subprocess.py`:
  - Spawns child process (per-backend venv via `uv run --project <backend-venv-path>` or similar)
  - Health-checks the child's HTTP shim
  - Forwards synthesize/synthesize_stream calls via HTTP
  - Manages child lifecycle (warmup, restart on crash, graceful shutdown)
- [ ] Spawn-venv strategy: backend extras (e.g., `[piper]`) install into a per-backend venv at `~/.voice-forge/backends/<name>/.venv/`. Pre-flight check on `load()`: if venv missing, error with a clear hint to run `voice-forge backend install piper`.
- [ ] New CLI command: `voice-forge backend install <name>` — creates the per-backend venv, installs the backend's deps
- [ ] Tests: `test_subprocess_backend.py` — use a fake subprocess that echoes input as audio (small WAV); verify lifecycle (start, synth, stream, restart-on-crash)
- [ ] Update `docs/ARCHITECTURE.md` with the subprocess pattern diagram
- [ ] LEARNING entry: design tradeoffs of the IPC choice
- [ ] Commit: `feat(backends): subprocess-isolated backend pattern + per-backend venvs`
- Agent: python-expert (it's a fair-sized architectural piece + needs careful subprocess lifecycle)
- Estimated: ~1 day
- Risk: medium — subprocess lifecycle bugs are notoriously hard to test. Mitigate with explicit timeout + restart-on-crash + structured logging on the child.

- [ ] [CHECKPOINT] After Phase 4: foundation in place for any backend with hostile deps. Phase 4 complete.

## Notes

- **No PyPI publish** in this plan — explicit user choice (option A skipped). After this work lands and stabilizes, tagging v0.3 to PyPI is the obvious follow-up.
- **No bearer auth** in this plan — explicit user choice (option B skipped). voice-forge stays localhost-only this iteration; auth re-engages when we have a token-issuance story (see QUEUED entry to be added during Phase 0).
- **Order rationale.** Phase 1 (foundations) is parallel-safe + low-risk; Phase 2 (demo UX) is independent of new backends and can ship first to validate the data model; Phase 3 (observability) gets us metrics before backends 3+4+5 land so we capture their latencies cleanly; Phase 4 (subprocess) is the architectural piece that unblocks Phase 5; Phase 5 (backends) is parallelizable additions; Phase 6 closes everything out.
- **Risks called out per phase** above. The biggest remaining one is subprocess lifecycle (Phase 4).
- **Effort estimates** are calibrated to "focused agent or developer working uninterrupted." Calendar time depends on review cadence.
